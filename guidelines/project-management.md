# プロジェクト管理ガイドライン

## 目的
部門横断プロジェクトおよび大型タスクの計画・実行・管理の標準手法を定める。

## 適用範囲
2部門以上が関与するタスク、または期間1ヶ月以上のプロジェクトに適用。

## プロジェクト分類

| 分類 | 規模 | 期間 | 管理レベル |
|---|---|---|---|
| S（小規模） | 1〜2部門 | 〜2週間 | 簡易管理（進捗報告のみ） |
| M（中規模） | 2〜3部門 | 2週間〜3ヶ月 | 標準管理（WBS + 週次報告） |
| L（大規模） | 3部門以上 | 3ヶ月超 | フル管理（WBS + ガントチャート + 週次報告 + ステコミ） |

## フェーズ分割の原則（大型タスクプロトコル）

### なぜフェーズ分割が必要か
- コンテキストの肥大化を防ぐ
- 各フェーズで品質チェックポイントを設ける
- フェーズ間の引継ぎで情報を構造化する

### フェーズ分割のルール
1. 1フェーズは1〜2週間で完了できる単位にする
2. 各フェーズの成果物を明確に定義する
3. フェーズ間の引継ぎ情報は要約形式（A4 1〜2枚）にまとめる
4. 各フェーズ終了時に品質レビュー部のチェックを受ける

### 引継ぎ情報のフォーマット
```
【プロジェクト名】
【前フェーズ】フェーズ名
【成果物】完成した成果物の概要
【残課題】未解決の課題
【次フェーズへの申し送り】次フェーズで考慮すべき事項
【リスク・懸念事項】継続的に監視すべきリスク
```

## 並列起動の設計原則

### Agent toolによる並列起動ルール
1. **独立したタスク**は並列起動する
   - 例: 財務DDとIT DDは並列で実施可能
2. **依存関係があるタスク**は順次実行する
   - 例: バリュエーションはDD完了後に実施
3. **生成と評価**は必ず分離する
   - 例: CFOがレポート作成 → 品質レビュー部が評価

### 並列起動の判断フロー
```
タスクを分解
├── 依存関係なし → 並列起動
├── 依存関係あり → 順次実行
└── 生成タスク → 完了後にレビュー部を起動
```

## 進捗管理

### ステータス定義
| ステータス | 説明 | 色 |
|---|---|---|
| Not Started | 未着手 | 灰 |
| In Progress | 進行中（予定通り） | 青 |
| At Risk | 進行中（遅延リスクあり） | 黄 |
| Blocked | 障害により停止中 | 赤 |
| Completed | 完了 | 緑 |

### 報告ルール
- S: 完了時に報告
- M: 週次で進捗報告
- L: 週次で進捗報告 + 月次でステアリングコミッティ

## リスク管理
- プロジェクト開始時にリスクアセスメントを実施
- リスク発生時はリスク管理部と連携
- Criticalリスクは即座にエスカレーション

## 完了基準
- 全成果物が完成し、品質レビュー部の承認を得ていること
- 残課題がリスト化され、担当・期限が明確であること
- 教訓（Lessons Learned）が文書化されていること
