# 月次経営分析(島村楽器)

このスキルは、`monthly_review` パッケージで機械的に検出した注意点を出発点に、
Claude が追加の切り口で裏付けを取り、**経営者向けの結論メモ**を作るための手順です。
機械判定だけで結論を出さず、必ず「多角的に確認してから結論」の順で進めます。

## 手順

### 1. データの確認
- 入力フォルダ(例: `data/2026-10/`)に5ファイルがあるか確認する。仕様は `docs/data_spec.md`。
- 足りないファイル・列があれば、ユーザーに不足分を伝えて止まる。推測で補わない。
- GRANDIT等の出力形式のままなら、仕様の形式に変換するスクリプトを書いてから進める(元ファイルは上書きしない)。

### 2. ツールの実行
```bash
pip install -r requirements.txt   # 初回のみ
python -m monthly_review --data data/2026-10 --month 2026-10 --out output
```
出力: `output/YYYYMM/report.html`(経営者向け)、`report.md`(Obsidian向け)、`detail.xlsx`(明細)、`findings.json`(Claude用)

### 3. データ品質を最初に見る
`findings.json` の `area == "データ品質"` が「中」以上なら、分析結論を出す前にユーザーへ報告し、
元データの抽出条件を確認してもらう。整合しないデータで結論を書かない。

### 4. 多角的な検証(必須)
`findings.json` の重要度「高」「中」それぞれについて、`references/analysis_playbook.md` の観点で
**最低2つの別の切り口**から裏付けを取る。pandas で `detail.xlsx` や元CSVを直接集計してよい。

確認の基本セット:
1. **時間軸**: 単月か、3か月・12か月でも同じ傾向か(季節性・曜日・催事日程のずれを除く)
2. **分解**: 店舗×部門、客数×客単価、ミックス×レート、入会×退会 のどれが効いているか
3. **横比較**: 同エリア・同業態の店舗と比べて固有の問題か、全社共通か
4. **領域横断**: 販売の不振が教室会員の減少と同じ店舗で起きているか、在庫や人件費と連動しているか
5. **金額の重み**: 営業利益への影響額で優先順位を付ける(件数ではなく金額)

検証の結果、機械判定が誤検知(一過性・データの癖)と判断できるものは、メモで「重要度を下げた理由」を明記する。

### 5. 結論メモの作成
`references/memo_template.md` の構成で `output/YYYYMM/executive_memo.md` を作る。ルール:
- 冒頭に結論を2〜3文。その後に根拠と具体策。
- **事実と推測を分ける**。推測には「(推測)」を付け、確信度を「高/中/低」で示す。
- 楽観的な見立てだけでなく、リスクとダウンサイド(放置した場合の年間影響額の目安)を必ず併記する。
- 外部要因(市場動向・競合・為替・メーカー値上げ)に触れる場合は、Web検索で裏付けを取り出典を書く。
  裏付けが取れなければ「未確認」と書く。
- 減損・評価損・引当金・税務に関わる示唆は「会計監査人・税理士への確認が必要」と明記する。
- 文体はです・ます調。定型の前置き、em-dash、過度なカタカナ語は使わない。
- 数値は必ずツール出力かコードでの再計算値を使う。暗算で書かない。

### 6. 報告
ユーザーには、結論2〜3文、重要度「高」の論点、検証で判断が変わった点、データ上の限界を短く伝え、
`report.html` と `executive_memo.md` のパスを示す。

## しきい値の調整
`config/thresholds.json` で変更できる。誤検知が多い項目は、ユーザーと合意したうえで調整し、
変更理由をコミットメッセージに残す。決算期の開始月は `fiscal_year_start_month` で設定する。

## 動作確認
```bash
python -m monthly_review --sample   # ダミーデータ(実在の数値ではない)で一連の出力を作る
```
